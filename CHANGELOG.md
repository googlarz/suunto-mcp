# Changelog

Versions on npm: 0.14.1, 0.14.4, 0.15.1 and later. The tags v0.14.0, v0.14.2, v0.14.3, v0.14.5 and v0.15.0 exist on GitHub but were never published to npm. Pre-0.15.1 notes are in the GitHub Releases.

## 0.25.1
- Heart-rate data-quality flag (new pure module `hr-quality.ts`, `assessHr`): from the FIT's record-level HR it returns `{ reliable, reasons, coverage }`. `reliable` is `false` when a rule fires, `true` when none does, and `null` when the FIT has no heart rate at all (reported as "no HR data", never as unreliable). Rules, each with a lenient threshold so a normal session is not flagged: under 80% of the session covered (dropouts are gaps of over 10 s between plausible samples, so the sampling rate does not matter: 1, 2 or 5 s between samples is no dropout; the session length is the FIT's timer time, else the span of its records, and a pause is not held against it); more than 2% of samples outside 30-230 bpm; the same value for over 180 s (a gap of over 10 s ends a run); at least 5 jumps of over 40 bpm between samples at most 2 s apart that are more than 1% of such pairs (not evaluated where samples are further apart). Thresholds are named constants in `hr-quality.ts`, each tested on both sides.
- The plausible heart-rate range is now one constant pair (30-230 bpm) shared by `hr-quality.ts` and the rest profile's HR series. The rest profile used to accept up to 250 bpm; a sample of 231-250 is now dropped there too.
- `get_workout_rest_profile` returns `hrQuality`; when it is `false` the profile's `reliable` is `false` and `note` lists the reasons. The rest numbers are still returned, not dropped.
- `get_exercise_history`: sessions with unreliable HR are marked `reliable: false` (as before, the median end-of-rest HR counts reliable sessions only) and a note names those whose heart-rate data is unreliable, with the reasons (up to 5 dates, then a count); a session unreliable for another reason is marked but not named. With `name` the note covers only sessions that have a matching exercise; the index view (no `name`) lists all sessions in the range and does not mention the median, which it does not return. Sessions whose FIT has no HR get their own note. The verdict is stored with the session in the local cache, whose schema number is now 2: older cache entries are ignored and rebuilt on the next call (this release's version number already did that).
- `get_training_load` and `get_baselines` are unchanged: they use Suunto's own per-workout TSS and daily aggregates (sleep HRV, recovery, steps), not the FIT's per-sample HR, so there is nothing to flag.
- Demo mode: the fifth most recent gym session loses its heart rate for the middle half of the session, so the flag shows up in `get_workout_rest_profile` and `get_exercise_history` there.

## 0.25.0
- `push_strength_guide`: new optional per-exercise `last` and `target` (strings such as `3x8@60kg` and `3x8@62.5kg`). When either is given, the exercise's prep step pops a `TODAY` notification, `Last <last> > <target> | <name>` (the hint at most 36 characters like the detail line, the whole text cut to 54; when the hint is too long `last` is shortened to its top reps (`10/10/10/10/8@102.5kg` becomes `10@102.5kg`), then dropped so the target stays whole, and if even that does not fit there is no popup: a number is never cut). Only a popup: step texts, and so lap labels, `get_workout_laps`, `compare_workout_to_plan` and `get_exercise_history`, are unchanged. How the popup renders on the watch is not checked on a device.
- `get_exercise_history` with `name` returns `suggestion: { last, target, reason }` (new field, computed by the pure function `suggestProgression` in `history.ts`): `last` is the newest session as `3x8@60kg` (or `8/8/6@60kg` when the reps differed), `target` is the same sets and reps with a load step on top when a `log_session` entry shows every planned set done with every planned rep at ONE weight, otherwise a repeat. The step is 2.5 kg but at most 5% of the load (in 1.25 kg steps, never below 1.25 kg: a 5 kg dumbbell goes to 6.25, 100 kg to 102.5). Sets logged at different weights (`8@60, 8@60, 8@70`, or some without a weight) never produce an increase: repeat at the lowest weight that reached the reps, and `last` shows each set (`8@60/8@60/5@65kg`). Without a logged session the watch's plan is all there is, so it repeats it and says so. A rep range in any spelling (`3x8-12`, `3x8 - 12`, `3x8–12`, `3 x 8 to 12`), a missing load or an unreadable detail never produces an increase. Nothing is pushed: pass `suggestion.last` / `target` to `push_strength_guide` yourself.
- New tool `forecast_training_load` (read-only): CTL, ATL and TSB for planned days (`days: [{ date, tss }]`, up to 120 days after `asOf`, default today and never in the future: a future `asOf` is refused; a date left out is a rest day), rolled forward from `get_training_load`'s current values with the same 42-day/7-day constants. Demo mode works on the synthetic data. CLI: `forecast-training-load <YYYY-MM-DD:TSS>... [--as-of DATE]`.
- New tool `adjust_guide` (read-only): takes a strength guide spec and returns it adjusted to today's recovery, with the reasons; it pushes nothing. HRV and recovery on waking come from `get_baselines`: neither below your band, or no reading: unchanged (never adds load); one below: one set less on exercises with 3+ sets (the `NxM` in `detail` is rewritten to match); both below: also loads 10% lower in 2.5 kg steps. A plate breakdown is dropped when the load changed; an exercise's `target` is dropped whenever that exercise changed at all (a set cut alone included), and `reasons` says so (`last` stays). Only the first `NxM` and `<n>kg` in `detail` are rewritten; an exercise whose detail does not match keeps its sets and says so.
- New tool `push_week_plan` (write): one new strength guide per date from a list of `push_strength_guide` specs (at most 14, unique dates, no `guideId`). **`dryRun` defaults to true** and then only validates and builds every guide and reports what it would push, with no network call. With `dryRun: false` the guides are pushed one after the other in date order through the same path as `push_strength_guide` (queued, read back from the guide list); the first failure stops the push and the result lists what was pushed, what failed and what was not pushed. Pushing the same plan again creates duplicate guides. In demo mode it writes nothing, even with `dryRun: false`.
- `log_session`: optional `tags` (array of at most 8 strings of 1-24 characters), stored on the entry. Tags are trimmed (the length limit applies after trimming); a control character, an empty tag or a duplicate (ignoring case) is refused with its position. A call with only tags does not replace the stored entry: it sets its tags and keeps the note, feeling and exercises (`replaced` still returns the previous entry); with no stored entry a tags-only entry is created. `get_exercise_history` does not show or use tags.

## 0.24.0
- New tool `get_exercise_history` (writes only a local cache, never Suunto): progression of strength exercises across guided sessions. Without `name` an index of the exercises in the range (sessions, last date, last detail); with `name` one row per session: the load (the first `NNkg` in the guide's label text, null when there is none, or the top weight from a `log_session` entry), sets done and planned, the guide's rest, the heart-rate recovery of the rest after set 1 (end HR, drop, seconds to fall 20 bpm, coverage), the exercise's deviation codes, `reliable`, the journal entry; plus first and last load and a median end-of-rest HR (usable as `push_strength_guide`'s `restTargetHr`). `weeks` 1-26 (default 8) ending at `date`. Built from the same functions as `get_workout_laps`, `compare_workout_to_plan` and `get_workout_rest_profile`. Weights and reps are what the guide planned, not measured. Reads at most 8 uncached sessions per call (newest first, one after the other) and reports `pending`; a session that fails is skipped and listed in `errors`. Name matching ignores case, accents and punctuation; a name the guide cut to 40 characters matches by prefix and is grouped with its longer form in the index, but only when that is certain: the cut name has at least 12 characters and exactly one longer name was seen; otherwise the names stay separate and a note lists them. A `BW+10kg` label has no load (an addition to bodyweight is never guessed). If sessions cannot be cached (the folder is not writable) or keep failing, the note says calling again will not help instead of `call again until pending is 0`, and sessions that failed are tried after the untried ones. Malformed entries in the journal file are skipped and counted in a note; in demo mode the journal file is not read. Sessions are returned as `cols`/`rows` to keep 26 weeks of one exercise under 6 KB (without journal notes, which are as long as you wrote them). CLI: `get-exercise-history [name] [--weeks N]`.
- New tool `log_session` (writes only a local file, never Suunto): records what actually happened in a session (note, feeling, per exercise sets with reps, kg, RPE, note) in `~/.suunto-mcp/journal.json`, one entry per `workoutKey`; logging a key again replaces its entry and returns the previous one (so the tool is marked destructive). A call with no note, no feeling and no exercises is refused (`nothing to log`) instead of wiping the entry, and unknown fields at any level are refused with an error naming the field instead of being dropped. The file is read again just before each write so an entry logged by another server process is kept; a journal file whose `version` is not 1 is refused, not rewritten. Strict limits: reps 0-200, kg 0-1000, RPE 1-10, texts 500 characters, 40 exercises, 20 sets each.
- Local files: `get_exercise_history` caches the derived result of each finished session in `~/.suunto-mcp/cache/<workoutKey>.json` (`SUUNTO_CACHE_DIR` moves it, `SUUNTO_CACHE=off` disables it; folder 0700, files 0600, written atomically; entries carry a schema number and the version of the server that wrote them, and an entry from another schema or another version is ignored; sessions under 24 hours old and failed reads are never cached). `SUUNTO_JOURNAL_PATH` moves the journal. Both are listed in the README under *Local files* and *Disconnecting*.
- Demo mode: `SUUNTO_DEMO=1` starts the server on synthetic data with no credentials, no token and no network call, so the tools and prompts can be tried while Suunto still reviews your API application. About 8 weeks ending today, generated deterministically (a seeded generator, so the same day always holds the same data): 3 guide-labelled gym sessions a week (one with a planted forgotten lap press, so `compare_workout_to_plan` shows a deviation), 1-2 runs a week with TSS, nightly sleep with stages, score and HRV plus occasional naps, recovery every 30 minutes, daily steps and energy, two routes, three guides (`list_guides` answers in Suunto's `{ error, payload, metadata }` shape with every field of a listed guide), and a small FIT file with heart rate for `get_workout_fit` and `get_workout_rest_profile`. The demo client only replaces the HTTP layer, so snapshots, baselines, training load and lap shaping run the normal code.
- Demo results are marked in one place: every successful tool result (and resource) is JSON with a top-level `"demo": true`; a list or plain-text result (such as a GPX file) becomes `{ "demo": true, "data": … }`. Errors are unchanged. The server instructions, the prompts and the startup line say demo mode is on.
- In demo mode every tool that is not read-only (`upload_workout`, `upload_route`, `push_*_guide`, `delete_guide`, `generate_daily_digest`, `log_session`) writes nothing and returns a short note on what it would do with real credentials.
- `npm run doctor` with `SUUNTO_DEMO=1` reports demo mode and skips the credential and network checks. Without `SUUNTO_DEMO` nothing changes. The CLI commands do not use demo mode.

## 0.23.0
- New tool `get_baselines` (read-only): your own recent norms, so a day can be judged against them. For the `days` days before `date` (14-90, default 28; `date` itself is never part of its baseline) it reports, per metric (`sleepDurationS`, `sleepScore`, `hrv`, `recoveryMorning`, `recoveryLow`, `steps`): `n` (days with a value), `median`, `p25`, `p75` (linear interpolation between order statistics; null below 7 days of data), `last7Median` (null below 4 values), `latest` (the value for `date`; always null for `steps` and `recoveryLow`, the day is still running) and `latestVsBand` (`below` / `within` / `above` the p25-p75 band). Sleep metrics come from the main sleep of the night that led into each day, as in `get_daily_snapshot`; a day without data is left out, never counted as 0. One request each for sleep and recovery, activity in pieces of up to 28 days (Suunto's limit); a failing section empties its metrics and is listed in `errors`. The band is the middle half of your own days, not a medical reference.
- Prompts: `suunto-gym-today` now calls `get_baselines` and cuts intensity 20-30% when `metrics.hrv.latestVsBand` or `metrics.sleepScore.latestVsBand` is `below` (before, it had nothing to compare HRV with); with no band it says there is too little history. `suunto-morning` calls `get_baselines` and sets sleep, HRV and waking recovery against your own band.
- New prompt `suunto-gym-review` (optional `date`, default today): finds the day's guided sessions in `get_daily_snapshot`, runs `compare_workout_to_plan` and `get_workout_rest_profile` on each, checks `reliable` first, and reports sets against plan, deviations with their basis and rest recovery.
- CLI: new read-only commands `get-training-load <date> [--days N]`, `compare-workout <workoutKey>` (without a plan), `get-workout-rest-profile <workoutKey>`, `get-route <routeId>`, `list-routes` and `export-route <routeId>` (prints the GPX). They call the same functions as the matching MCP tools.

## 0.22.0
- `push_strength_guide`: the guide's list icon is now a blue-violet gradient with a white barbell instead of flat grey. Other guides keep the grey icon. How it renders in the Suunto app is not yet checked on a device.
- `push_strength_guide`: step titles now carry both counters: prep `3/6`, set `3/6 - 2/3`, a rest `3/6 REST` (its text still starts with `Next:`), and with `perExercise` the work step is `3/6` (up to 13 characters for 10 of 12 exercises with 10 sets; 3-digit set counts are cropped). Before, set and rest steps showed only the set counter. Lap labels come from step text, so `get_workout_laps`, `compare_workout_to_plan` and `get_workout_rest_profile` are unaffected. How the longer titles render on the watch is not yet checked on a device.
- `push_strength_guide`: set popups now read `SET 2/3` with `<name> - <detail>`; the last set of an exercise pops `LAST SET` with `Next: <next exercise>` (the final exercise: its own name and detail); `perExercise` keeps `GO`. When name and detail together exceed the watch's 40-character text limit, the name is shortened first, on set and prep steps; the plates/detail line is kept up to 36 characters (a longer one is cut too) so the name keeps at least 3. Lap labels change only when one of these cuts applies, and `compare_workout_to_plan` matches a shortened name to the plan by prefix; a name cut down to a few letters can match the wrong exercise if two names share that start.
- `push_strength_guide`: new optional `restTargetHr` per exercise (integer 41-200 bpm): adds a heart-rate gauge from 40 to that value right after the live HR on that exercise's between-set rests (countdown and stopwatch). Gauge rendering is not yet checked on a device.
- `push_strength_guide`: the guide's list description now names the day's exercises (`Bench · Row · Squat`, cut at 60 characters; the limit is a guess) instead of `6 exercises`.
- New tool `get_workout_rest_profile` (read-only): per-rest heart-rate recovery of a guided gym session, from the FIT file's record-level HR joined to the guide's laps (exercise, set). Per rest: peak HR (the highest 3-sample-smoothed value from 15 s before to 30 s after the rest starts, for optical HR lag), end HR, total drop, `t10S`/`t20S`/`t30S` (seconds after the peak until the smoothed HR fell 10, 20, 30 bpm), bpm per minute over the first minute, sample count and coverage; medians per exercise. Shows recovery that `compare_workout_to_plan` cannot (with restMode `countdown` the rest lap lasts exactly its target). Optional `plan` as for `compare_workout_to_plan`. The rest windows use the lap table's `startTime` as time zero; how that lines up with the FIT timeline is not yet checked against a real workout. `alignment` reports both start times, and a FIT session start more than 10 s from it makes the result unreliable.
- `get_workout_fit` summary (full=false) gains `developer`: the SuuntoPlus app's developer fields in the FIT (`apps`, `fields`, `devChannels`), or null when the FIT has none. All existing fields are unchanged. Whether Suunto's FIT files carry app developer fields is unverified.

## 0.21.0
- MCP prompts (new `prompts` capability): `suunto-morning`, `suunto-weekly` and `suunto-gym-today`, one-click workflows in clients that show prompts. Each takes an optional date (`date` or `endDate`), validated as a real calendar date (invalid values are an invalid-params error), and writes the explicit dates and tool calls into the prompt text.
- `get_workout_samples`, `export_workout_gpx` and `list_subscriptions` are no longer listed to the model: Suunto rejects them (OperationNotFound). Calling one by name returns an error saying so. Set `SUUNTO_ENABLE_LEGACY_TOOLS=1` to bring them back. The CLI commands are unchanged.
- `push_workout_guide`, `push_interval_guide`, `push_strength_guide` and `upload_workout` now report whether the write arrived, not only that it was sent. Guide pushes read the guide back from the guide list (by id, by name if Suunto returned no id) and add `check: { verified, note? }`. `upload_workout` polls the upload status for up to about 20 s and adds `status` and `check: { verified, note? }` (`verified` once the status is `Processed`). Existing result fields are unchanged.
- Guide pushes and workout uploads are queued one at a time per process with a short pause (`SUUNTO_WRITE_GAP_MS`, default 2000), like route imports since 0.19.2, so several calls at once are safe. `SUUNTO_UPLOAD_POLL_MS` (default 2000) sets the pause between upload status polls.
- New tool `get_training_load` (read-only): Fitness (CTL), Fatigue (ATL) and Form (TSB) per day for up to 120 days ending at `date` (default 28), with weekly totals, the 7-day ramp rate and `notes`. Computed from workout TSS with the digest's model; reads 120 days of warm-up before the window so it isn't cold-started from 0, or starts from `seedCtl`/`seedAtl`. CTL can be about 1 point off the watch. Reports when the 500-workout limit is reached instead of hiding it.
- The digest's CTL/ATL maths moved to `src/training-load.ts`, shared by both; digest output is unchanged.
- New tool `compare_workout_to_plan` (read-only): maps the laps of a guided gym session (`push_strength_guide` perSet or perExercise, countdown or stopwatch, and `push_workout_guide`) to exercises, sets and rests, and reports planned against actual with deviations that each name their basis (`labels`, `plan` or `heuristic`). The optional `plan` is the exercises array that was pushed (`name`, `sets`, `restSec` are read). `no-heart-rate` stays in `checks` but does not make the result unreliable. Stopwatch and workout-guide label formats are derived from the guide code and not yet checked against a real session.
- `get_workout_laps`: the description and a code comment no longer say that prep and set labels look alike (their halves are swapped) or that laps after "Session complete" have no label (they carry it). Text only, no behaviour change.

## 0.19.0

Each `<rte>`/`<trk>` becomes its own PRIVATE route, named from the file; `activities` (default `[1]`) is set by the call, not by the GPX. Only real `.gpx` files up to 10 MB are accepted. ## 0.18.1
- **Security:** `upload_workout` accepts only `.fit` and `.gpx` files, and only uploads to an `https` URL.

- Dependencies: `npm audit` clean; `@modelcontextprotocol/sdk` floor raised to 1.31.
- `get_daily_snapshot`: an invalid `date`/`to` is an error everywhere (CLI included); reaching the workout limit is reported in `errors` instead of silently dropping workouts; limit is 25 workouts per day.
- `get_workout_laps`: a lap pressed after the guide's "Session complete" lap no longer triggers `unlabelled-laps`.
- CLI: `get-daily-snapshot --to` with no value is an error.
- CI: pinned action SHAs, read-only permissions, smoke test of the packed tarball.
