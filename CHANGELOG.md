# Changelog

Versions on npm: 0.14.1, 0.14.4, 0.15.1 and later. The tags v0.14.0, v0.14.2, v0.14.3, v0.14.5 and v0.15.0 exist on GitHub but were never published to npm. Pre-0.15.1 notes are in the GitHub Releases.

## 1.1.0
Three features for keeping honest score of your own judgement. Everything is additive within the 1.x contract: ten new tools (the server now lists 52 by default), one new optional input of `log_session`, two new local files and environment variables, no change to an existing name, type or annotation. The contract fixtures (`test-fixtures/contract/`) were regenerated on purpose and the diff is additions only.

- **Prediction ledger** (new tools `log_prediction`, `void_prediction`, `score_predictions`, `get_prediction_stats`; file `~/.suunto-mcp/predictions.json`, `SUUNTO_PREDICTIONS_PATH` moves it). A prediction is written down before the fact with a probability from 0 to 1, an optional `rule` label and a `note`, and is immutable: no edit, no delete, only `void_prediction` with a reason. Its `date` (YYYY-MM-DD; there is no workoutKey form) must be strictly after today by the server's local date and at most 60 days ahead, for every kind. A voided prediction stays in the ledger and in the counts, apart from the scored ones; a void is allowed only on a day strictly before `date`, and cannot be undone (annotated destructive). A prediction identical to one still open (same kind, date and kind-specific fields; probability, note and rule do not count) is refused with the id of the open one. Four kinds the server scores itself: `session_done` (a workout exists on the date), `hrv_in_band` (the night after the date against the user's 28-day p25..p75 band, as `get_baselines` computes it, edges inclusive), `recovery_morning_at_least` (the Balance on waking after that night, at least `threshold`, compared as printed), `reps_hit` (an exercise, `sets` x `reps`, optionally at `kg` or more, on the date: scored from `log_session` entries; a logged set without a weight takes the guide label's; without logged sets only fewer set laps than predicted in a reliable per-set guide proves a miss). Only workouts that started after the prediction was made count as evidence. `score_predictions` resolves every prediction that is due (the second day after the date, because a day's data may sync late) as `hit`, `miss` or `unresolvable` (data truly missing: never guessed). When a workout or a night is missing, the prediction stays **pending** (unscored, listed in `pending` with its reason) until the watch has synced data from a later day; only then is it a miss (no workout) or unresolvable (no night), so a missing sync is never scored. A failed request is not `unresolvable` either: the prediction stays unscored and the error is reported. Outcomes are final; `rescoreUnresolvable: true` reads the unresolvable ones again (after the never-scored ones, so a call always advances through what is new) and writes only a changed answer. At most 20 predictions per call (oldest due first, `remaining` says how many are left), so the same call twice scores the next batch and is annotated not idempotent. A `reps_hit` scored from a journal entry with `source: "draft"` carries `basis: "draft-confirmed"` in its outcome, and `get_prediction_stats` reports those apart (`basis`: hit rate with and without them, each shown from 20). `get_prediction_stats`: per kind and per `rule`, the count, hits, hit rate, Brier score, the Brier score of always saying the overall hit rate, and a calibration table (5 buckets of stated probability), with **`insufficient` under 20 scored predictions** (every rate and the table are null: the 95% interval of a 50% hit rate is still about +-22 points at 20) and a bucket's observed rate hidden under **5** predictions. Voided, unresolvable and unscored ones are counted and never scored.
- **Randomized self-experiments** (new tools `start_experiment`, `get_experiment`, `log_experiment_day`, `analyze_experiment`, `stop_experiment`; file `~/.suunto-mcp/experiments.json`, `SUUNTO_EXPERIMENTS_PATH` moves it). `start_experiment` takes a name, the intervention and the control in words, an outcome metric (`sleepDurationS`, `sleepScore`, `hrv`, `recoveryMorning`: the night after each assigned day, the same per-night values `get_tag_effects` uses), `days` 14-60, optional `eligible` weekdays, `washout` 0-2 days after each intervention day (never analysed) and an optional `startDate` (default tomorrow; not in the past). It pre-registers the hypothesis and the analysis plan in the file and draws the whole schedule up front with a seeded generator (mulberry32; the seed is stored, the schedule is never redrawn): eligible days are taken in order two at a time, each pair holding one intervention and one control day in random order, so the arms are exactly balanced (a last unpaired day is dropped). A design with fewer than 6 days per arm is refused. One active (upcoming or running) experiment per outcome metric. `log_experiment_day` records whether the day was followed; a corrected answer keeps the earlier one under `earlier`. `analyze_experiment` reports the difference of medians (intervention minus control), a two-sided permutation test over the randomized pairs (the arms swapped within each pair; **all swaps are enumerated up to 15 informative pairs, else 20000 random swaps with the fixed seed 20261115**, so the same data always gives the same p). With no washout a swapped pair is a schedule the draw could equally have produced, so the p-value is exact when the intervention does nothing; **with a washout it is an approximation**, checked by a seeded simulation (about 3% false positives at a nominal 5% with carry-over between nights, for washout 0, 1 and 2), and the stored analysis plan and the result (`pValueBasis`) say so, the effect against `get_tag_effects`' noise threshold, nights per arm and missing nights, for **intention to treat** (primary) and **per protocol** (only days logged as followed; not protected by the randomization). Verdict: **`insufficient` under 6 nights with a value in either arm** (with 6 pairs the smallest possible two-sided p is 2/2^6 = 0.031; with 5 it is 0.0625, so 6 is the least that can ever show anything), else `intervention-higher` / `intervention-lower` only when **p <= 0.05 and the median difference is larger than the noise threshold** (compared as printed), else `no-clear-difference`. The statement says in plain words what was randomized and what was not controlled. Allowed from the second day after the planned end; `early: true` is exploratory and flagged, as is a stopped experiment. `stop_experiment` keeps everything but cannot be undone (annotated destructive).
- **Zero-logging draft** (new tool `draft_session_log`, read-only): for a `workoutKey` (or the latest guided session on a `date`) it proposes the `log_session` payload from `compare_workout_to_plan`'s mapping and the guide's text, sets x reps @ load, **all marked `assumed: true`** because the watch records the plan, not what was lifted. In a per-set guide the set count is the number of set laps; otherwise the plan's, and the user must confirm it. It lists every deviation (missing, extra, short, long sets, rest splits, laps after "Session complete", an unreliable mapping, a session that stopped early, missing exercises with `plan`), the heart-rate quality of the session, and the exact things to ask. `3x40m` is not read as reps; a missing weight is left out. It never writes: the client calls `log_session` after the user confirmed.
- `log_session` gained an optional `source` (only `"draft"`). The mark is stored apart from the entry, in a top-level `sources` map of `journal.json` next to `entries`, not inside the entry: I checked 1.0's reader, which refuses an entry with a field it does not know and then skips the whole entry (the entry would vanish from `get_exercise_history`, `get_tag_effects` and the rest), but ignores a top-level key it does not know. So a 1.0 server still reads every entry in full. The one loss: a 1.0 server that writes the journal back rewrites the file without `sources`, so the draft marks (and with them `basis: "draft-confirmed"`) are lost, while every entry stays. An entry without a source is exactly what 1.0 wrote.
- Demo mode: the ledger and the experiments run on in-memory stores (nothing reaches the disk) and start with deterministic synthetic data: a month of due predictions to score and one finished experiment with its log. `draft_session_log` works on the demo's gym sessions.
- CLI: new `get-prediction-stats` and `get-experiment [ID]` (local files only, no credentials), `analyze-experiment [ID] [--early]` and `draft-session-log <workoutKey> | --date D` (read-only). Logging, voiding, scoring, starting, logging days and stopping are MCP-only because they write.
- Local state: both files carry `"version": 1`, are written atomically (0600, folder 0700), re-read right before each write, strict about unknown fields, and a damaged, foreign or newer-version file is refused with its name and left untouched (shared code in `src/local-store.ts`). Annotations: `log_prediction`, `start_experiment`: not read-only, not destructive, not idempotent, not open-world; `log_experiment_day`: not read-only, not destructive, idempotent, not open-world; `void_prediction`, `stop_experiment`: not read-only, destructive (cannot be undone), idempotent, not open-world; `score_predictions`: not read-only, not destructive, not idempotent, open-world; `get_prediction_stats`, `get_experiment`: read-only, not open-world; `analyze_experiment`, `draft_session_log`: read-only, open-world.
- Tests: boundary tests for every threshold and minimum n (both sides), determinism tests for the generator, the schedule and the permutation test (a pinned value, and an independent brute-force enumeration against the Monte Carlo branch), a seeded false-positive simulation of the test, refusal tests for damaged, foreign and newer-version files, and demo-mode tests that nothing is written.
- README: new section "Predictions, experiments and session drafts", the two environment variables, the two local files, the ten tools in the reference table and a limit under "Known limits" (the thresholds are design choices checked on synthetic data, not on real nights).

## 1.0.0
1.0 declares the interface stable. Within 1.x the names (tools, `bin` commands, environment variables, MCP prompts and resources), input schemas and documented output fields stay compatible (new tools, optional inputs and output fields may be added, and an input may accept more), annotations change only toward more caution, and the local file formats are versioned or rebuildable. Everything inside the contract is removed only in 2.0; the three hidden legacy tools (`get_workout_samples`, `export_workout_gpx`, `list_subscriptions`, which Suunto no longer answers) are deprecated and outside it, and may be removed in a 1.x minor release. Any removal is announced here first and the item keeps working for at least one more minor release. What is promised and what is not is in [docs/CONTRACT.md](docs/CONTRACT.md); what has not been verified on a real watch or real Suunto files is in the README's "Known limits / not yet verified on real devices". The server lists 42 tools by default. Below, the features added since 0.25.1 and what the release itself changed.

- Contract tests: `src/contract.test.ts` starts the real server in demo mode (clock frozen, no network) and compares `tools/list` (every tool's name, input schema without description text, annotations) and the key shape of every read-only tool's result (keys and value types, never values; arrays by the union of their items) with `test-fixtures/contract/tools.json` and `outputs.json`. Any difference fails and says whether it is BREAKING (removed or renamed tool or property, changed type, new required input, changed annotations) or additive. An addition is allowed only on purpose: `UPDATE_CONTRACT=1 npm test` rewrites the fixtures (see CONTRIBUTING.md).
- Contract test, extended: annotations may change only toward more caution (a more cautious change is "additive with notice", a less cautious one BREAKING); an input that accepts more (new enum value, higher maximum, lower minimum, lifted limit) is additive and one that accepts less is BREAKING; description and example text is not compared. The output shapes are recorded after a plan is set (so `get_plan`, `get_catchup` and `get_weekly_report` show their plan shape), on a day with a workout, with `compare_workout_to_plan` given a plan, and with `push_week_plan` as a dry run; `test-fixtures/contract/outputs.json` has an `unobserved` section listing every field demo data never fills. New `surface.json` fixture for the `bin` commands, the environment variables the code reads, MCP prompts (with arguments) and MCP resources; a test also requires every variable the code reads to be in the README's table.
- Demo mode: `push_week_plan` now runs its dry run (the default, which contacts nothing) instead of returning the demo note; `dryRun: false` still only returns the note.
- The daily digest history (`SUUNTO_HISTORY.md`) and the `sync-to-health-skill` state file are now created with mode 0600, like the other local files (an existing file keeps its mode).
- `push_strength_guide` (tool description and README): states that how step titles and popups render on a real watch is not yet verified on a device.
- Version test (`src/version.test.ts`): `package.json`, `server.json` (twice), `manifest.json` and `package-lock.json` (twice) must all carry the same version. The server reads its version from `package.json`; no source file holds one.
- README: new section "Known limits / not yet verified on real devices" (guide popups and titles on the watch, future-dated guides, location-triggered guides, units of `recoveryTime` / `pte` / `peakEpoc`, FIT integrity check and heart-rate quality thresholds, `get_tag_effects` false-alarm rates, the route-time model, the `.mcpb` bundle, deleting a route).
- README: the environment-variable table now lists `SUUNTO_ENABLE_LEGACY_TOOLS`, `SUUNTO_DAILY_PREFIX`, `SUUNTO_HEALTH_EXPORT_STATE_PATH` and the four write-pacing variables, which the code read but the README did not name. CONTRIBUTING no longer says MCP prompts are not wired up (they are).
- `get_weekly_report`: the workouts table's Total (and the summary line's total) is now the sum of the rows as they are printed, each rounded to the minute, so a reader adding the Duration column gets the Total (before, three rows of 41 min could sit above a Total of 2 h 02 min). The JSON `workouts.totalTimeS` is unchanged: the exact sum in seconds.
- `parseFit`: a file with a valid FIT header but a body that is not FIT records now fails with `not a readable FIT file (the data after the header could not be decoded)` instead of the parser's internal "Cannot read properties of undefined (reading 'globalMessageNumber')". The parser's own error is kept as the error's `cause`.
- New tool `get_weekly_report`: a shareable report for one finished Monday-to-Sunday week (`week` = its Monday, default the last full week; a week that has not ended, a non-Monday and an invalid date are refused). It assembles the week's workouts (from `get_daily_snapshot`), sleep duration, sleep score, HRV, recovery on waking and steps as the week's median (at least 4 days with a value) against the user's own 28 days before the week (`get_baselines`'s middle half: below / within / above, edges within), training load at the end of the week (CTL/ATL/TSB, the week's TSS and the week before), the week's guided strength sessions (`get_exercise_history`, `pending` passed on), plan adherence (a planned date with any workout is done, else missed; `adherencePct` null with no session planned) and tag effects (only a tag whose verdict is not `insufficient`; otherwise the markdown says so). The result has the structured sections, `markdown` (self-contained, for sharing: no account id, token, workout key or file path), `saved`, `errors` (a failing section is null and listed) and `notes`. Reads about 30 requests from Suunto and changes nothing there. `save: true` also writes `~/.suunto-mcp/reports/week-<Monday>.md` (`SUUNTO_REPORTS_DIR` moves it; file 0600, a folder it creates 0700, written complete and linked into place); the same content again is `unchanged`, a different existing file is refused (`saved.status: "refused"`, the report is still returned) unless `overwrite: true` (replaced atomically); `overwrite` without `save` is refused. Annotated not read-only and destructive (through `overwrite`), idempotent. Demo mode runs it on an in-memory store with a synthetic-data notice at the top of the markdown and writes nothing to disk. CLI mirror `get-weekly-report [MONDAY] [--markdown]` (never saves). In the shared markdown every user-written text (guide, exercise and tag names, plan goal and titles) is escaped (`|`, `<`, `>`, `&`, backticks, brackets, a leading `#` / list marker; newlines collapse); an unreadable plan reads "Unavailable", not "No plan was set"; the workouts table has a Total row and the week's training stress is that same sum (the load model's own figure is stated when it differs); steps read "N over D of 7 days"; developer-facing load notes are replaced by plain sentences.
- New tool `estimate_route_time` (read-only): a saved route's time from the user's own pace. It reads the route's GPX (one request) and the local archive (`archive_workouts`; no other Suunto request), cuts the route and each archived walking/hiking (or `activity: "running"`) workout's FIT records (distance, altitude, time; pauses over 30 s dropped) into 100 m pieces and fits, by least squares, time = flat pace x distance + extra per metre climbed + extra per metre descended on the newest 25 usable of the 40 newest archived workouts. It needs at least 3 workouts of 1 km or more, 15 km of track, 300 m of climbing and 300 m of descent and a plausible fit; otherwise `model.status` is `insufficient` with the reason and the estimate is the generic Naismith rule (5 km/h + 1 h per 600 m climbed), labelled `basis: "generic-naismith"`. Returns the total, flat / ascent / descent splits (at or beyond 3 % gradient; stretches under 300 m merged), the model's constants and its in-sample error, and with a user-supplied `sunset` (ISO 8601 with offset; nothing is looked up) the latest start minus `marginMinutes` (default 30). A route without altitude on every point is estimated as flat ground, with a note. Stretches steeper (up or down) than anything the model was fitted to are counted in `estimate.outsideRangeM` / `splits[].outsideRangeM`, with a note, instead of being extrapolated silently. CLI mirror `estimate-route-time`. The archive store gained `readFit`. `parseFit` now refuses bytes that fail the archive's header and length check (`checkFit`, moved to `fit.ts`) with a clear error before they reach `fit-file-parser`, which can spin forever on bytes that are not a FIT file: this covers `get_workout_fit`, `get_workout_rest_profile`, the CLI, the exercise history and the route estimate.
- New `.mcpb` one-click bundle: `manifest.json` (MCPB manifest spec 0.3) and `npm run pack:mcpb`, which builds, installs the production dependencies (without optional ones) into `build/stage/` from the lock file and writes `build/suunto-mcp-<version>.mcpb` (a compressed zip of manifest, runtime `package.json`, licence, `dist/` and `node_modules/`; `build/` is gitignored). Secret-like names (`.env*`, token and credential files, keys) are never packed, a test checks the listing and contents of a produced bundle, and the manifest version must equal `package.json`'s. `manifest.json` lists all 42 tools statically (a test compares the names with the server's `tools/list`; `tools_generated` is not used) and has `privacy_policies` pointing at the README's Privacy section. Settings: a `demo` checkbox (on by default, translated to `SUUNTO_DEMO=1` by the bundle's entry point `dist/mcpb-entry.js`) and optional sensitive client ID, client secret and subscription key plus the app name. It adds no new sign-in: pairing for real data stays the existing `suunto-mcp-auth`. Unverified: opening it in a real host, signing, auto-update, host-side substitution of booleans and empty options. `buildZip` takes an optional `{ compress: true }` (deflate, valid DOS date); the default output for guide uploads is unchanged.
- New tools `set_plan` and `get_plan`: the training plan as local state in `~/.suunto-mcp/plan.json` (`SUUNTO_PLAN_PATH` moves it; version 1, folder 0700, file 0600, written atomically, read again right before each write). `set_plan` takes a `goal`, optional `start` / `end`, `phases` (`name`, `from`, `to`, `focus`) and `sessions` (`date`, `title`, optional strength-guide `guide`, whose `date` must equal the session's); `mode: "replace"` (default) makes the call the whole plan, `"merge"` replaces goal, start, end or phases when given and merges sessions by date (start and end cannot be cleared in a merge; use replace). Strict: unknown fields, invalid dates, `from` after `to`, sessions or phases outside `start`..`end` (when both are given), duplicate dates, and more than 20 phases, 200 sessions, 500 characters of text (100 for names and titles) or 8000 characters of guide JSON are refused and nothing is written; a plan file that is damaged, invalid or of another version is refused and never overwritten. A replace overwrites the stored plan, so `previous` in the result is the complete plan it replaced (null when there was none) and the tool is annotated destructive. `get_plan` (read-only) returns the plan (without guide bodies), the current phase, today's session with its guide and the 7 days after today (a null session is a rest day), or one `date`. Neither tool needs Suunto credentials (MCP and CLI): they only touch the local file. The plan never pushes anything to the watch: `push_week_plan` / `push_strength_guide` stay the only way. Annotations: `set_plan` is not read-only, destructive, idempotent, not open-world; `get_plan` is read-only, not open-world.
- New tool `get_catchup`: what is new since the last catch-up. New workouts (date, start, activity id, duration, TSS, guide), new finished nights (sleep, score, HRV, recovery on waking), new recovery samples, plan items in the review window as done / missed / pending by date only (any workout on a planned date counts as done), and days since the last session. It only reads from Suunto: workouts in pages of 50 (51 asked for, so exactly 50 is complete; at most 4 pages per call), sleep and recovery in one list call each. The first call looks back 7 days (the list calls add a margin of up to 14 hours for time zones); later calls start at the review window's first day, never more than 14 days back (older is reported in `notes`), and list workouts 2 days further back so a late sync is found. The marker lives in `~/.suunto-mcp/seen.json` (`SUUNTO_SEEN_PATH` moves it) and moves only when `markSeen: true` is passed; without it the call is a pure read and repeats the same answer. The marker holds the keys of the workouts already reported (a bounded list: a workout that syncs late with an earlier start than one already seen is still new, once), the end of the latest night and the newest recovery sample seen, a cursor when the workout list was longer than one call reads (the next call continues below it), and the review window's first day. That day moves forward only when every section was read (no failed section, a readable plan file, the whole workout list), so what a failed section missed shows up on the next call; a failed section also keeps its own marker. An unreadable plan file is listed in `errors`. A night still being recorded and naps are not reported. A damaged or other-version `seen.json` stops the call and is never overwritten. Annotations: not read-only (`markSeen: true` writes the marker, so clients may ask for permission), not destructive, idempotent, open-world.
- Demo mode: `set_plan`, `get_plan` and `get_catchup` run on in-memory stores (they live as long as the server process and write no file); every other write tool still only returns its note.
- CLI: new read-only commands `get-plan [date]` (no credentials needed) and `get-catchup` (the terminal never moves the catch-up marker).
- Tests: the stdio and demo checks that classified every tool by name and annotation now know the local-only tools.
- New tool `get_tag_effects` (read-only): do the nights after sessions carrying a `log_session` tag differ from the nights after other sessions? Per tag and per metric (`sleepDurationS`, `sleepScore`, `hrv`, `recoveryMorning`, the same per-night values `get_baselines` bands, now taken from one shared function `nightMetrics`) it compares the nights that followed a day with a tagged session with those that followed other training days, over `days` nights (30-180, default 90) ending the day before `date` (the night into `date` itself may still be recording and is left out). A rest day is in neither group, a session without a journal entry counts as untagged, a day with several sessions is one night (tagged when any session is), tags match ignoring case; a session that starts after midnight counts on its own calendar day (said in `notes`, not remapped). Output per tag: tagged sessions and nights, untagged nights, a one-sentence `statement` (n, the minimum, "an association, not a cause"), and per metric n of each group (nights with a value), both medians, median and mean difference, the untagged nights' IQR, the threshold and a verdict. **Thresholds**: a metric is `insufficient` below **15** tagged or **15** untagged nights with a value; otherwise `tagged-higher` / `tagged-lower` only when `|median(tagged) - median(untagged)| > K * 1.25 * (IQR_untagged / 1.35) * sqrt(1/nTagged + 1/nUntagged)` with **K = 3** (equal is `within-noise`; compared as printed, i.e. rounded). That is K standard errors of the difference of two medians (1.25 sigma / sqrt(n) is the standard error of a median, IQR / 1.35 a robust sigma). The tag's verdict is `differs` when any of the 4 metrics is higher or lower, `insufficient` when all are, else `within-noise`. K was chosen with a seeded simulation (`tag-effects.test.ts`): K = 2.5 flagged 17% of tags at 15 nights per group with no real difference, K = 3 does not exceed 12% (asserted). With K = 3 and independent nights and no real difference it flags about 9% of tags at 15 nights per group, 5% at 20 and 3% at 30 (the test asserts at most 12%), and 11% to 22% when nights are correlated 0.3; a real shift of 1.5 IQR at 20 nights per group is flagged in at least 93% of simulations. `notes` state the thresholds, the 4 metrics, the false-alarm figures and that it is an association, not a cause. An unreadable journal file is an error. Demo mode uses a small synthetic journal (`strength`, `long-run`) and never reads the real file. CLI: `get-tag-effects [--days N] [--tag T] [--date D]`.
- New tools `archive_workouts` and `get_archive_status`: a local copy of every workout, so the history does not depend on how far back Suunto's list reaches. Per workout `<workoutKey>.fit` (as Suunto sent it) and `<workoutKey>.json` (the list item with its summary and intensity extensions, the FIT's size and SHA-256) in `~/.suunto-mcp/archive/` (`SUUNTO_ARCHIVE_DIR` moves it; files 0600, and a folder the tool creates is 0700: an existing folder keeps its mode). Each file is written complete under a temporary name and then hard-linked to its final name, which fails if the name exists, so even another process racing for the same workout cannot overwrite a file (the folder's filesystem must support hard links). The record is written last and marks the workout archived, so an interrupted call is completed by the next one. Incremental and bounded: a workout with a record is skipped, at most 20 FIT files are downloaded per call (`limit` 1-20, newest first; the newest 1000 workouts are read from the list), `remaining` says how many are still missing, and keys that failed are retried after the others. Each download is checked before anything is written (non-empty, a 12 or 14 byte FIT header with `.FIT` at byte 8, not shorter than header size + data size + 2 CRC bytes; the CRC itself is not checked, and the length rule is checked against the FIT specification and the demo files, not against a real Suunto download); a bad download writes nothing and is listed in `errors`. Nothing is ever deleted or overwritten: a record that is not valid, of another version, filed under another key or with extra fields, a missing FIT file, a FIT file whose size differs from its record, and a FIT file already there that differs are reported (`refused`, `errors`, `problems`) and left as they are; files in the folder that are not `<key>.json` / `<key>.fit` are ignored. `get_archive_status` (read-only, local files only, no credentials) reports archived count, FIT bytes, oldest and newest date and every problem; it checks each FIT file by size and does not re-hash. A FIT file with no record (an interrupted call) is listed by `get_archive_status` as `incomplete`, not counted as archived, and completed by the next `archive_workouts` when the download is identical. Annotations: `archive_workouts` is not read-only, not destructive, not idempotent (each call archives the next batch), open-world; `get_archive_status` is read-only, not open-world. Demo mode keeps the archive in memory and writes nothing to disk. Not wired into `get_exercise_history` or `get_training_load`: the history needs the laps (not in the archive) and the load needs a merge with the live list, which is more than a small change. CLI: `get-archive-status` (no credentials); `archive_workouts` is MCP-only because it writes.
- New tool `get_benchmark` (read-only apart from `get_exercise_history`'s cache): one repeatable session as a series. `guide` (the guide title from the workout list, matched ignoring case, accents and punctuation) or `exercise` (as in `get_exercise_history`), over `weeks` weeks (default 8, max 26). Per occurrence (an exercise that appears twice in one session is merged into one entry: heaviest block's detail, load and reps, sets added, median rest HR, `parts` blocks): duration and TSS from the workout list, median end-of-rest heart rate, and per exercise load (the label's weight, or the logged one with `loadSource` journal), planned reps (the `NxM` in the label; null for a range), sets, end-of-rest heart rate (reliable sessions only). Per series: n, first, last, best (highest load and reps, lowest duration and heart rate; none for TSS) and a trend. **Trend rule**: with at least 3 values the median of the older half (the first floor(n/2)) is compared with the median of the newer half (the last floor(n/2); the middle one is left out when n is odd); `up` / `down` when they differ by more than 3% of the older median (exactly 3% is `flat`), else `flat`; below 3 values `insufficient`. No significance test. It reads sessions through the same code as `get_exercise_history` (now `collectRecords`, extracted from `buildExerciseHistory` without a change in what that tool returns): same cache, same 8 uncached sessions per call and `pending`. CLI: `get-benchmark --guide T | --exercise N [--weeks N]`.
- Demo mode: `archive_workouts` runs on an in-memory archive; every other write tool still only returns its note.

## 0.25.1
- Heart-rate data-quality flag (new pure module `hr-quality.ts`, `assessHr`): from the FIT's record-level HR it returns `{ reliable, reasons, coverage }`. `reliable` is `false` when a rule fires, `true` when none does, and `null` when the FIT has no heart rate at all (reported as "no HR data", never as unreliable). Rules, each with a lenient threshold so a normal session is not flagged: under 80% of the session covered (dropouts are gaps of over 10 s between plausible samples, so the sampling rate does not matter: 1, 2 or 5 s between samples is no dropout; the session length is the FIT's timer time, else the span of its records, and a pause is not held against it); more than 2% of samples outside 30-230 bpm; the same value for over 180 s (a gap of over 10 s ends a run); at least 5 jumps of over 40 bpm between samples at most 2 s apart that are more than 1% of such pairs (not evaluated where samples are further apart). Thresholds are named constants in `hr-quality.ts`, each tested on both sides.
- The plausible heart-rate range is now one constant pair (30-230 bpm) shared by `hr-quality.ts` and the rest profile's HR series. The rest profile used to accept up to 250 bpm; a sample of 231-250 is now dropped there too.
- `get_workout_rest_profile` returns `hrQuality`; when it is `false` the profile's `reliable` is `false` and `note` lists the reasons. The rest numbers are still returned, not dropped.
- `get_exercise_history`: sessions with unreliable HR are marked `reliable: false` (as before, the median end-of-rest HR counts reliable sessions only) and a note names those whose heart-rate data is unreliable, with the reasons (up to 5 dates, then a count); a session unreliable for another reason is marked but not named. With `name` the note covers only sessions that have a matching exercise; the index view (no `name`) lists all sessions in the range and does not mention the median, which it does not return. Sessions whose FIT has no HR get their own note. The verdict is stored with the session in the local cache, whose schema number is now 2: older cache entries are ignored and rebuilt on the next call (this release's version number already did that).
- `get_training_load` and `get_baselines` are unchanged: they use Suunto's own per-workout TSS and daily aggregates (sleep HRV, recovery, steps), not the FIT's per-sample HR, so there is nothing to flag.
- Demo mode: the fifth most recent gym session loses its heart rate for the middle half of the session, so the flag shows up in `get_workout_rest_profile` and `get_exercise_history` there.

## 0.24.0
- New tool `get_exercise_history` (writes only a local cache, never Suunto): progression of strength exercises across guided sessions. Without `name` an index of the exercises in the range (sessions, last date, last detail); with `name` one row per session: the load (the first `NNkg` in the guide's label text, null when there is none, or the top weight from a `log_session` entry), sets done and planned, the guide's rest, the heart-rate recovery of the rest after set 1 (end HR, drop, seconds to fall 20 bpm, coverage), the exercise's deviation codes, `reliable`, the journal entry; plus first and last load and a median end-of-rest HR (usable as `push_strength_guide`'s `restTargetHr`). `weeks` 1-26 (default 8) ending at `date`. Built from the same functions as `get_workout_laps`, `compare_workout_to_plan` and `get_workout_rest_profile`. Weights and reps are what the guide planned, not measured. Reads at most 8 uncached sessions per call (newest first, one after the other) and reports `pending`; a session that fails is skipped and listed in `errors`. Name matching ignores case, accents and punctuation; a name the guide cut to 40 characters matches by prefix and is grouped with its longer form in the index, but only when that is certain: the cut name has at least 12 characters and exactly one longer name was seen; otherwise the names stay separate and a note lists them. A `BW+10kg` label has no load (an addition to bodyweight is never guessed). If sessions cannot be cached (the folder is not writable) or keep failing, the note says calling again will not help instead of `call again until pending is 0`, and sessions that failed are tried after the untried ones. Malformed entries in the journal file are skipped and counted in a note; in demo mode the journal file is not read. Sessions are returned as `cols`/`rows` to keep 26 weeks of one exercise under 6 KB (without journal notes, which are as long as you wrote them). CLI: `get-exercise-history [name] [--weeks N]`.
- New tool `log_session` (writes only a local file, never Suunto): records what actually happened in a session (note, feeling, per exercise sets with reps, kg, RPE, note) in `~/.suunto-mcp/journal.json`, one entry per `workoutKey`; logging a key again replaces its entry and returns the previous one (so the tool is marked destructive). A call with no note, no feeling and no exercises is refused (`nothing to log`) instead of wiping the entry, and unknown fields at any level are refused with an error naming the field instead of being dropped. The file is read again just before each write so an entry logged by another server process is kept; a journal file whose `version` is not 1 is refused, not rewritten. Strict limits: reps 0-200, kg 0-1000, RPE 1-10, texts 500 characters, 40 exercises, 20 sets each.
- Local files: `get_exercise_history` caches the derived result of each finished session in `~/.suunto-mcp/cache/<workoutKey>.json` (`SUUNTO_CACHE_DIR` moves it, `SUUNTO_CACHE=off` disables it; folder 0700, files 0600, written atomically; entries carry a schema number and the version of the server that wrote them, and an entry from another schema or another version is ignored; sessions under 24 hours old and failed reads are never cached). `SUUNTO_JOURNAL_PATH` moves the journal. Both are listed in the README under *Local files* and *Disconnecting*.
- Demo mode: `SUUNTO_DEMO=1` starts the server on synthetic data with no credentials, no token and no network call, so the tools and prompts can be tried while Suunto still reviews your API application. About 8 weeks ending today, generated deterministically (a seeded generator, so the same day always holds the same data): 3 guide-labelled gym sessions a week (one with a planted forgotten lap press, so `compare_workout_to_plan` shows a deviation), 1-2 runs a week with TSS, nightly sleep with stages, score and HRV plus occasional naps, recovery every 30 minutes, daily steps and energy, two routes, three guides (`list_guides` answers in Suunto's `{ error, payload, metadata }` shape with every field of a listed guide), and a small FIT file with heart rate for `get_workout_fit` and `get_workout_rest_profile`. The demo client only replaces the HTTP layer, so snapshots, baselines, training load and lap shaping run the normal code.
- Demo results are marked in one place: every successful tool result (and resource) is JSON with a top-level `"demo": true`; a list or plain-text result (such as a GPX file) becomes `{ "demo": true, "data": … }`. Errors are unchanged. The server instructions, the prompts and the startup line say demo mode is on.
- In demo mode every tool that is not read-only (`upload_workout`, `upload_route`, `push_*_guide`, `delete_guide`, `generate_daily_digest`, `log_session`) writes nothing and returns a short note on what it would do with real credentials.
- `npm run doctor` with `SUUNTO_DEMO=1` reports demo mode and skips the credential and network checks. Without `SUUNTO_DEMO` nothing changes. The CLI commands do not use demo mode.

## 0.23.0
- New tool `get_baselines` (read-only): your own recent norms, so a day can be judged against them. For the `days` days before `date` (14-90, default 28; `date` itself is never part of its baseline) it reports, per metric (`sleepDurationS`, `sleepScore`, `hrv`, `recoveryMorning`, `recoveryLow`, `steps`): `n` (days with a value), `median`, `p25`, `p75` (linear interpolation between order statistics; null below 7 days of data), `last7Median` (null below 4 values), `latest` (the value for `date`; always null for `steps` and `recoveryLow`, the day is still running) and `latestVsBand` (`below` / `within` / `above` the p25-p75 band).
